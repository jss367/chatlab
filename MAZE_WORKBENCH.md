# Maze navigation workbench

Enable **Maze experiments** under **Settings → Extensions**, restart ChatLab, then open **Maze** to run and inspect one navigation episode. Load a Qwen2.5 Instruct model on **Models** first. The current action parser recognizes Qwen-style `<tool_call>` envelopes; other tool protocols need their own parser. The model may emit arbitrary text, make an invalid call, or stop without acting.

## Use

1. Select maze size, maze seed, shortest route length, and open-cell probability. Some combinations cannot produce a maze; the generator reports this rather than changing the requested length.
2. Choose **Goal information**: **Exact coordinates** gives the model the destination's row and column; **Hidden location** tells it a destination exists and asks it to explore; **Hint only** supplies your required **Goal hint** without adding destination coordinates. Write a clue about the destination shown on the board, and check it again if you change the maze settings. Hidden and hint modes reset supplied starting moves to 0. You can deliberately supply moves, but they demonstrate the shortest route toward the goal.
3. Choose interruption text, token count, and timing. Timing counts accepted moves, including supplied moves. The interruption is inserted into the next assistant response. **None** runs a clean control.
4. Click **New episode · apply settings**, then **Run episode** or **Step one response**. Editing controls alone does not change the current episode.
5. Watch the character and path alongside generated tokens. Click tokens for probabilities and alternatives. The exact supplied prefix is shown separately, and the full raw response retains both parts. For a reasoning model, tokens emitted inside its exposed reasoning block remain visible; these are not access to hidden internal reasoning. Qwen2.5 Instruct has no separate reasoning channel.
6. **Pause after response** waits for the current response to end. **Stop now** retains partial tokens and does not execute a partial action. **Interrupt next response** overrides the scheduled insertion time, recording the run as manually intervened.
7. Select a response under **Path and replay** to inspect its board and tokens, or walk the episode with **◀ Previous** and **Next ▶**. **Play from here** advances from the selected response to the last one at **Playback seconds per response**, and **Stop playback** ends it, as does toggling the shortest-route overlay; **Previous** and **Next** still work afterwards. Playback only redraws this view, so it works on a finished episode and on a saved replay, which is what **Run episode** refuses to do. Pause a live episode before stepping or playing it back. Export JSON, or upload a previous export to step through and play back, and to fork it (step 8).
8. To change generated output, pause or stop the episode, select a response, and click a token. Under **Edit selected token**, enter **Replacement text** or choose an exact alternative under **Replacement token**, then click **Replace token and regenerate**. Completed episodes can be edited too, as can a run uploaded in step 7, provided the model that produced it is loaded. A recorded alternative applies in the session that offered it; on a run from another session, type the branch you want under **Replacement text**. Regeneration finishes one response; use Run or Step to continue.

Token editing saves the original run and creates a new run with the maze, message history, and recovery state rewound to just before the edited response. This is also how you fork an uploaded run: the edit rebuilds it as a live episode instead of reopening the saved one, so you do not have to reconstruct its maze and settings by hand. Earlier token IDs in that response are kept exactly, the selected token is replaced, and its remaining output and later moves are regenerated. Replacement text may encode to several tokens. The retained tokens and replacement appear in the supplied prefix panel and do not count toward the new continuation's sampled-token limits; completed earlier responses keep their token counts. The exported JSON records the parent run, its model and load identifiers, whether the parent was an uploaded replay, the edited response and token index, the original token ID, and the replacement IDs. Edited runs are marked as manual interventions.

An uploaded run itself stays read-only: Run, Step and **Interrupt next response** all refuse it, and its file is never rewritten, so a stale snapshot cannot overwrite a newer archive of the same run. Editing a token is the way into a live episode. Editing needs the same model ID loaded. Reloading those weights, or loading them in a later session, is enough as long as that load tokenizes the run the same way, because what the fork replays is token IDs. Supplied prefix tokens remain read-only. Loading a *different* model requires starting a new episode. A fork continues under the weights in memory at the time, so it first verifies what it is about to replay. Each earlier response, which the fork rebuilds from its stored IDs, and the edited response itself have to decode from those IDs to the text they recorded when they were generated. The comparison reads each response whole, because decoding is not piecewise: a vocabulary revision that respells an ID from a word-boundary piece to a plain one leaves it decoding alone to the same characters while the sequence around it reads differently, and a byte-level piece of a character decodes alone to a replacement character whatever bytes it carries. Read in place, both of those show up in the text the response records. The edited response is checked in full, past the edited token as well as before it, because boundary semantics only mean anything in context and a vocabulary that has moved anywhere in that response is evidence the tokenizer is not the one that produced the run. Each earlier response also has to still end the way it recorded, so a response that stopped naturally still ends on a token the loaded model treats as a stop token. The retained tokens of the edited response have to contain no stop token of the loaded model, because the runtime cuts a forced prefix at its first stop token and the response would otherwise end before reaching the token you selected. The alternative chosen for the edited token is the one ID the fork replays with no recorded response behind it, and the run records it by decoding that ID on its own, which says nothing about how the model that offered it spelled the ID in place. A word-boundary piece and a plain piece record the same text that way, so a vocabulary spelling the ID either way reproduces the recording while the branch after the retained tokens reads differently. A recorded alternative is therefore applied only in the session that offered it, whose load identifier names the weights in memory now. A run uploaded from another session is refused, as is a live run whose weights have been reloaded since, because a load identifier restarts its numbering in each session and so cannot show that the tokenizer is unchanged. **Replacement text** reaches the same branch on those runs and is checked more strictly: typed text is encoded and checked in place after the retained tokens, so the ID it picks is the one that spells what you typed in that position under the loaded vocabulary. The selected alternative still has to be one the run recorded for that token, which is a question about the selection rather than the tokenizer. The edit is refused when any of that disagrees, which is how a re-download of the same repository ID at a revision with a different tokenizer is caught before it rewrites the retained prefix or rebuilds the earlier turns from the wrong maze position. The run JSON keeps both stamps.

A dashed path marks supplied moves; the solid indigo path marks actual accepted model moves. The amber ring marks the position where the interruption was inserted. The board always shows you the destination, including in hidden and hint modes. The shortest-route overlay is only for the viewer, never part of the prompt. The status reports the current episode's goal mode; editing the selector affects the next new episode.

## Run locally

Use the repository's normal Python environment and dependencies:

```sh
python app.py
```

Set `CHATLAB_MAZE_RUNS_PATH` to override the default `~/.local/share/chatlab/extensions/maze_experiments`. Completed responses and terminal states are autosaved there. Existing ChatLab conversations remain separate. A model loaded in Chat or Models is shared with Maze, and generation is mutually exclusive across views.

## Protocol and interpretation

The entire map, coordinate labels, current position and legal directions are visible to the model in all goal modes. Destination coordinates appear in the initial prompt and tool replies only in **Exact coordinates** mode (the default). **Hidden location** and **Hint only** omit destination coordinates from every simulator message, including errors and supplied-move history; hint mode includes your clue verbatim. The simulator confirms arrival when the model steps onto the destination. The actual goal remains in the viewer's board and saved JSON for inspection and scoring, and exports preserve the selected mode and hint. Older exports default to exact coordinates.

Each accepted `move(maze_id, direction)` advances exactly one cell. A tool-looking example inside a code fence, blockquote or reasoning block is not executed. Multiple or malformed calls return a tool error. A complete response with no attempted call ends the episode as abandonment; the controller sends no reminder. A response cut off by a limit does not execute its unfinished action.

Default settings mirror the planned pilot: 5×5 maze, shortest distance 10, three supplied canonical moves, an 8-token interruption, temperature 0.7, 1,024 sampled tokens per response, 8,192 per episode and 32 tool attempts. The first accepted move after insertion must occur within 1,024 sampled tokens / 4 attempts. Returning to movement is distinct from making progress toward the goal. Supplied tokens do not count toward sampled-token budgets. Stopping manually is not a failed recovery. A clean run has no post-interruption recovery score.

This is an exploratory workbench, not the batch experiment or a training implementation. Its configurable maze family and manual interventions should not be mixed into a preregistered evaluation unnoticed. No maze-trained adapter is bundled. The JSON includes configuration, simulator transitions, complete message history, actual prompt token IDs, output token IDs and probabilities, stop reasons and intervention provenance. Each new turn re-renders prior response text through the model's native template; this is disclosed rather than claiming uninterrupted token-stream identity across turns.

## Verification

`python -m unittest discover -s tests` runs the existing ChatLab suite plus simulator/controller tests. Maze tests cover goal disclosure across initial prompts and tool replies, settings callbacks, hidden-goal identifiers, legacy and new replay formats, deterministic maps and route length, blocked/fake/quoted/unfinished actions, supplied-token accounting, recovery and arrival, abandonment, pause/stop, response stepping and timed playback, token editing and state rewind, forking an uploaded replay under a later load of the same model, refusing that fork when the later load decodes a recorded response differently or cannot decode its IDs at all, when it respells a retained ID across a word boundary while every ID still decodes alone as it did, when it moves the bytes of a fragment the response completes, when a vocabulary moved past the edited token, when an earlier response no longer ends on a stop token, when the later load treats a retained token as a stop token, refusing a recorded alternative on a run the session did not produce, including one a respelled vocabulary would reproduce exactly, and reaching that branch by typing it instead, reading a supplied prefix special the way replay forces it and an export predating recorded per-token text like any other, allowing a recorded alternative in the live episode that offered it, leaving a newer archive of that run untouched, native tool-template forwarding and replay path validation.

The extension boundary and enable/disable lifecycle are documented in [Optional extensions for ChatLab](EXTENSIONS.md). Existing JSON exports remain compatible. Legacy `~/.local/share/chatlab/maze_runs` files remain available to upload.
