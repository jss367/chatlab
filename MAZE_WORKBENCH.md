# Maze navigation workbench

Enable **Maze experiments** under **Settings → Extensions**, restart ChatLab, then open **Maze** to run and inspect one navigation episode. Load a Qwen2.5 Instruct model on **Models** first. The current action parser recognizes Qwen-style `<tool_call>` envelopes; other tool protocols need their own parser. The model may emit arbitrary text, make an invalid call, or stop without acting.

## Use

The **One agent** tab runs a single episode; the **Team** tab runs several agents at once, described under [Team episodes](#team-episodes). The single-agent workbench has three panes: **Scenario** on the left, the maze and shared transport in the center, and tokens plus **Movement history** on the right. The scenario pane opens with the three things a session starts from, the model button, **Experiment trials** and **Load a saved run**, and the settings for a fresh episode follow under **New episode · apply settings**. Side panes scroll independently and can be resized using their lower corners. **Movement history** takes whatever height the right pane has spare, so a tall window shows more responses at once rather than empty space, and gives it back to the panels under it when they open. Narrow windows stack the panes.

1. Select maze size, maze seed, shortest route length, and open-cell probability. Some combinations cannot produce a maze; the generator reports this rather than changing the requested length.
2. Choose **Goal information**: **Exact coordinates** gives the model the destination's row and column; **Hidden location** tells it a destination exists and asks it to explore; **Hint only** supplies your required **Goal hint** without adding destination coordinates. Write a clue about the destination shown on the board, and check it again if you change the maze settings. Hidden and hint modes reset supplied starting moves to 0. You can deliberately supply moves, but they demonstrate the shortest route toward the goal.
3. Open **Setup prompt**, the first of those settings, to read or change the **System prompt** and the **Task instruction**, which is sent verbatim ahead of the JSON state. Each goal mode has its own stock instruction, so choosing a mode rewrites the box unless you have typed your own wording. Blank wording is sent as written: an empty system prompt, or the state with no instruction line. **Run details** reports whether the episode's prompt is default or edited.
4. Choose interruption text, token count, and timing. Timing counts accepted moves, including supplied moves. The interruption is inserted into the next assistant response. **None** runs a clean control.
5. Open **Waypoint & steering** to ask the model to pass through a cell on its way, to steer it with an activation vector partway through, or both. See [Waypoints and steering](#waypoints-and-steering).
6. Tick **Map can change during the run** to start an episode whose walls you can close while it is running. This is decided before the episode starts, because the identifier the model addresses the maze by is fixed from its first prompt. See [Changing maps](#changing-maps).
7. Click **New episode · apply settings**, then **Play** to keep going or **Next** to generate one response. Editing controls alone does not change the current episode.
8. Watch the character and path alongside generated tokens. Click tokens for probabilities and alternatives. The exact supplied prefix is shown separately, and the full raw response retains both parts. For a reasoning model, tokens emitted inside its exposed reasoning block remain visible; these are not access to hidden internal reasoning. Qwen2.5 Instruct has no separate reasoning channel.
9. Open **Context sent to the model** to read the whole prompt behind the selected response: the system prompt, the task instruction, the JSON state, the move tool's schema and description, the earlier responses and the simulator's replies, all as one text. A generated response is decoded from the prompt token IDs it recorded, so it reads as the template wrote it, down to the turn markers; a supplied prefix is not part of it and stays under **Supplied text & full response**. Those IDs are read back only by the model that recorded them, because a token ID is a position in one vocabulary and another model spells the same numbers as whatever it keeps at those positions - fluent text unrelated to the prompt, decoded without complaint, two vocabularies overlapping in size. So the pane compares the model that recorded the selected response with the loaded one, the run answering only for responses recorded before they carried their own name. An episode continues under whatever is loaded, so generating under one model, loading another and pressing Next leaves the run named after the first and the new response after the second, and each response is read back by the model that wrote it. A run that records no model at all, which only a file written elsewhere can be, is refused with them: an episode here takes the loaded model's name before its first response, and silence is not permission, since any model's reading would otherwise be offered as the record. A fork can be lenient about an unnamed run because it goes on to check each response against the text that response recorded; a pane reading one prompt has no such second witness. It asks once before spending a decode on a vocabulary that cannot mean the IDs, and again of the reading itself, which is the answer that decides what you see: the first can be a load behind, and being so costs a decode rather than changing a word of this. Where the two models differ the pane reads the prompt through the loaded model's template instead, names both models and says which one to load. The model it names is the one that spelled what you are reading, and where nothing spelled it - the messages shown untemplated - it is the one in memory as the line is written. The initial prompt has no recorded IDs to leave undecoded, so it is marked as one model's reading of another's messages instead. The initial prompt, which no response has been asked for yet, goes through the loaded model's own template too. With no model loaded, the pane shows the messages and tool schema as the run recorded them, and says which it is: nothing loaded, a load that landed while it was reading, or a loaded model whose template refused this history, which it names. A reading made under a load that is not the one that recorded the run is marked too. The pane reads on request rather than with every token, and names the response it read, so reopen or click **Show the selected response's context** after moving the selection.
10. **Pause** stops replay immediately or waits for a generated response to finish, keeping the episode resumable. **Stop now · end episode**, under **Playback & view**, retains partial tokens and does not execute a partial action. **Interrupt** queues the configured passage for the next generated response, overriding its scheduled insertion time and marking the run as manually intervened. The transport shows when an interruption is queued.
11. Click a **Movement history** row or choose **Selected response** to inspect the corresponding board position and tokens. The arrow marks the selected row; rejected calls and responses without a move are included. **First** returns to the initial history. **Previous** moves back one recorded response. **Next** advances one recorded response, or generates one at the live end. **Play** replays from the selection at the configured pace, then continues generating in an unfinished live episode. Finished episodes and uploaded runs stop at the end of their recordings. An uploaded run opens at its initial history, so **Play** replays it from the start. The transport shows **Replaying**, **Generating**, or **Paused**. Pause generation before navigating history. **Load a saved run** at the top of the scenario pane takes a run's JSON, and **Export the run** at the foot of it writes one. Uploading a run fills the whole scenario pane with the settings that run used, replacing whatever was there, so **New episode · apply settings** repeats the same scenario. Runs saved before the open-cell probability was recorded have it recovered from their maze, by searching every value for one that redraws it whole, walls, start and destination alike. Where no value does, the slider is left where it was and **Run details** says the probability is unrecorded, so a new episode from that pane draws a different maze.
12. To change generated output, pause or stop the episode, select a response, and click a token. In the editor that appears beside the output, enter **Replacement text** or choose an exact alternative under **Replacement token**, then click **Replace token and regenerate**. Open **Token probabilities** in the same editor to branch in one click instead: clicking a row forks the run into that alternative immediately, which is the same edit without the dropdown and the button. Right-clicking a token puts both choices where the token is: the alternatives the model weighed, each with its probability, and a box for text of your own. Picking one replaces the token and regenerates from it without crossing the pane, and the editor opens beside the output as it does for a click, so the token's measurements are there to read. Completed episodes can be edited too, as can a run uploaded in step 11, provided the model that produced it is loaded. A recorded alternative applies in the session that offered it; on a run from another session, type the branch you want under **Replacement text**. Regeneration finishes one response; use Play or Next to continue.

Token editing saves the original run and creates a new run with the maze, message history, and recovery state rewound to just before the edited response. This is also how you fork an uploaded run: the edit rebuilds it as a live episode instead of reopening the saved one, so you do not have to reconstruct its maze and settings by hand. Earlier token IDs in that response are kept exactly, the selected token is replaced, and its remaining output and later moves are regenerated. Replacement text may encode to several tokens. The retained tokens and replacement appear in the supplied prefix panel and do not count toward the new continuation's sampled-token limits; completed earlier responses keep their token counts. The exported JSON records the parent run, its model and load identifiers, whether the parent was an uploaded replay, the edited response and token index, the original token ID, and the replacement IDs. Edited runs are marked as manual interventions.

An uploaded run itself stays read-only: Play and Next only replay recorded responses, and **Interrupt** refuses it, and its file is never rewritten, so a stale snapshot cannot overwrite a newer archive of the same run. Editing a token is the way into a live episode. Editing needs the same model ID loaded. Uploading a run renames the model button under **Scenario** after the model that recorded it, and clicking it opens **Models** with that ID already in the box; reading the weights is still a click there, on **Load cached** or **Download and load**. Reloading those weights, or loading them in a later session, is enough as long as that load tokenizes the run the same way, because what the fork replays is token IDs. Supplied prefix tokens remain read-only. Loading a *different* model requires starting a new episode. A fork continues under the weights in memory at the time, so it first verifies what it is about to replay. Each earlier response, which the fork rebuilds from its stored IDs, and the edited response itself have to decode from those IDs to the text they recorded when they were generated. The comparison reads each response whole, because decoding is not piecewise: a vocabulary revision that respells an ID from a word-boundary piece to a plain one leaves it decoding alone to the same characters while the sequence around it reads differently, and a byte-level piece of a character decodes alone to a replacement character whatever bytes it carries. Read in place, both of those show up in the text the response records. The edited response is checked in full, past the edited token as well as before it, because boundary semantics only mean anything in context and a vocabulary that has moved anywhere in that response is evidence the tokenizer is not the one that produced the run. Each earlier response also has to still end the way it recorded, so a response that stopped naturally still ends on a token the loaded model treats as a stop token. The retained tokens of the edited response have to contain no stop token of the loaded model, because the runtime cuts a forced prefix at its first stop token and the response would otherwise end before reaching the token you selected. The alternative chosen for the edited token is the one ID the fork replays with no recorded response behind it, and the run records it by decoding that ID on its own, which says nothing about how the model that offered it spelled the ID in place. A word-boundary piece and a plain piece record the same text that way, so a vocabulary spelling the ID either way reproduces the recording while the branch after the retained tokens reads differently. A recorded alternative is therefore applied only in the session that offered it, whose load identifier names the weights in memory now. A run uploaded from another session is refused, as is a live run whose weights have been reloaded since, because a load identifier restarts its numbering in each session and so cannot show that the tokenizer is unchanged. **Replacement text** reaches the same branch on those runs and is checked more strictly: typed text is encoded and checked in place after the retained tokens, so the ID it picks is the one that spells what you typed in that position under the loaded vocabulary. The selected alternative still has to be one the run recorded for that token, which is a question about the selection rather than the tokenizer. It also has to be a token the loaded model shows in a response, asked of every run because it is a question about the model alone. The runtime drops a hidden special from the text it streams, so an alternative the model hides would leave the response reading exactly as it did while the token still entered the model's context. A hidden token that also ends a response is allowed, because ending there is an outcome you can see. The edit is refused when any of that disagrees, which is how a re-download of the same repository ID at a revision with a different tokenizer is caught before it rewrites the retained prefix or rebuilds the earlier turns from the wrong maze position. The run JSON keeps both stamps.

A dashed path marks supplied moves; the solid indigo path marks actual accepted model moves. The amber ring marks the position where the interruption was inserted. A cell closed during the run is drawn in brown, apart from the walls the maze started with. The board always shows you the destination, including in hidden and hint modes. The shortest-route overlay is only for the viewer, never part of the prompt. The status reports the current episode's goal mode and whether its setup prompt is default or edited; editing those controls affects the next new episode.

## Changing maps

A changing map is a second kind of perturbation, beside the interruption: the environment moves under the model rather than its own output being written into. Tick **Map can change during the run** before clicking **New episode · apply settings**, then open **Change the map** under the board, enter a row and a column, and click **Close this cell**. The cell becomes a wall before the next generated response.

The maze keeps one identifier for its whole run. `Maze.tool_id` hashes the grid, so closing a cell on an ordinary maze would rename it: the model's next call would carry the name it was given and come back `wrong_maze`, told it had addressed some other maze rather than that this one had changed. A changing map is identified instead by a handle fixed when the run starts, derived from the grid and start it begins with and never from the destination, so it discloses no more under **Hidden location** or **Hint only** than an ordinary hidden-goal run does.

The model is not told the map changed. Its next prompt is the history as already written, so the response generated after a closure still shows the cell open and may well walk into it. It meets the change in the simulator's reply, which carries the current grid whether the move was accepted or refused; a move into a cell that has just closed comes back `blocked_move`, under the identifier the model has had all along. The board and the exported JSON show the change from the moment it lands.

A closure has to leave a maze the run could have begun with, so the destination stays reachable from the start; the character has to be able to reach the destination from where it is standing, so a closure narrows the problem rather than ending it; and the cell the character occupies is never walled in. The start and the destination are never closed. Anything else is refused where you asked for it, naming which rule it broke.

One cell queues at a time, as one interruption does, and one closure belongs to a response: a second click while a closure is waiting is refused and names the cell already queued, and so is one asked for when the map has already changed before the response about to be generated. That last case is what a fork of the response after a closure starts in, since it carries that closure at the boundary it is about to regenerate. Replacing it would lose the first one entirely, since a closure that never lands is in neither the map nor the record of what the map refused. The refusal and the queueing are one operation, because the close button runs off the queue and two clicks arrive as two callbacks at once. Taking the queued cell and recording the map it produced is one operation for the same reason: a queue emptied ahead of the record would leave a moment showing a free queue beside a map that had not changed yet, and the run would record closing a wall.

A closure is checked again when it lands, because the character moves between the click and the next response. One that has become impossible by then is dropped: the run goes on, and the closure is recorded under `dropped_closures` with the reason, because a map that did not change after you asked it to reads exactly like a map nobody asked to change. **Run details** counts them. A cell still queued when the episode ends is dropped the same way, since no response is left to apply it, and it is dropped before the autosave of the response that ended the run rather than only on the way out, so the file left behind by a process that dies there is still one the workbench can read; a run exported while it is still waiting carries it under `close_next` instead, because that run can still reach it.

Changing runs are saved as `chatlab-maze-run-2`. Everything else in the file is as it was, with the map the run started from under `maze` and each closure under `config.map_updates` as the response boundary it landed before, the character's position at that moment, the cell, and the grid it produced. Uploading one replays every response against the version of the map it acted on, and refuses a file whose record does not hold: a closure out of order, two at one boundary, a position the run's path never reached, a grid the recorded closure does not produce, a closure the rules would have refused, an identifier that does not belong to the map the run starts from, or a transition the map of that moment never allowed. The closures a run reports dropping are checked too, since **Run details** reads them as provenance and every fork carries them: each names one response boundary the run reaches, in order, none shares a boundary with a closure the map took, and each names a cell the run could have queued there and a reason. A cell still pending is read the same way, waits for a response whose map has not already changed, and cannot be there at all in a run that has ended. A run carrying any of the three is refused if it reports that nobody intervened in it, since every closure begins as a request that marks the run. The reason itself is not re-derived, because a dropped closure left no version of the map behind to check it against, and a closure an episode ended under was never about the map at all. A `chatlab-maze-run-1` file carrying closures is refused rather than replayed as the map it started from. Ordinary runs are unaffected: they stay on `chatlab-maze-run-1`, record no closures, and refuse to make one.

Editing a token forks a changing run like any other. The fork keeps the closures that landed before the response being edited and replays them at their own boundaries, so the branch is judged against the map that response was acting on; the closures that came after are left behind with the responses that followed them. Closures the map refused are carried on the same rule, because the fork keeps the responses that ran after a failed intervention and would otherwise report that nobody had asked for one.

Closing a cell marks the run as manually intervened, as an interruption you request by hand does. The mark and the queue are set together and a run is written down as one reading, so an export taken while you are clicking cannot carry a closure while saying no intervention was made. The run is rendered under that reading rather than merely read under it, so a stop landing mid-export cannot write the same closure as pending and dropped at once. A trial file pins one map per trial and cannot yet schedule closures, so a changing run is driven by hand.

## Inserted messages

An inserted message is text someone other than the model placed in its context partway through a run: a note inside the simulator's reply, a message signed by a teammate, or a user turn. It is a third kind of perturbation beside the interruption and the changing map. The interruption writes into the model's own response; an insertion writes into what the model reads before it responds. The interruption stays the way to put words in the model's own reasoning: when the template opens a `<think>` block, the interruption's tokens are fed inside it, with no closing tag added.

Open **Insert a message** under the board, beside **Change the map**, choose a channel, write the text, name a sender for a teammate message, optionally pick an advised direction, and click **Queue this message**. It goes into the context before the next generated response. Each channel is written into the history one way, by one function, `render_insert` in `extensions/maze_experiments/inserts.py`, which generation, forks and the upload check all call:

- **Simulator note** (`tool_note`): the latest simulator reply's JSON object gains a final key, `"note": <text>`.
- **Teammate message** (`teammate`): the same reply gains a final key, `"messages": [{"from": <sender>, "text": <text>}]`, the shape a team run delivers a teammate's message in, so the message reads the same in both modes.
- **User message** (`user`): a new message `{"role": "user", "content": <text>}` goes after the latest simulator reply.

The reply keeps its compact separators and key order, and the new key comes last. The model is told nothing else. The simulator's next reply is the ordinary state, so a note appears once, in the reply it was added to, and stays there in every later prompt as history. A note or a teammate message needs a simulator reply to ride on, so one asked for before the first move of a run with no supplied moves is refused; a user message is not. The text cannot carry tool syntax, conversation boundary tokens or reasoning delimiters.

The advised direction is recorded for scoring and never sent. The run declares it; ChatLab does not read it out of the text. It may point into a wall, since bad advice is part of what an experiment varies.

The queue follows the closure's rules. One message is queued at a time, and a second request is refused naming the first. One message lands before a response, so a fork holding a message at the boundary it is about to regenerate refuses another until that response exists. Queueing marks the run as manually intervened, and the refusal, the queue and the mark are one operation under the episode's lock. A message still queued when the episode ends is dropped before the final autosave. It is not recorded, since no response read it. The same holds for a message whose response never reached the model: one landed before a response that is stopped at its opening frame, or whose model call fails before feeding its prompt, is taken back out of the history and the record.

A run carrying a message is saved as `chatlab-maze-run-3`, whether or not its map changes, so an older ChatLab refuses the file rather than reading every later response against a history shifted by one. Runs without one keep writing `chatlab-maze-run-1` and `chatlab-maze-run-2` exactly as before. Whether a format-3 run's map changes is read off its map, which a changing one saves with its environment identifier, and `config.map_updates` is then read under the changing-map rules above. Each message is recorded under `config.context_inserts`, in order:

```json
{
  "before_turn": 3,
  "channel": "tool_note",
  "text": "Heading east from here reaches the goal fastest.",
  "sender": null,
  "position": [2, 1],
  "advised_direction": "east"
}
```

`before_turn` is the index of the response the message landed before, as for a closure. `sender` names the teammate and is null on the other two channels. `position` is where the character stood at that boundary. `advised_direction` is `north`, `east`, `south`, `west` or null, and may be left out. Nothing else is recorded. A response's context is counted from this record: two messages for every call before it, plus one for every user message at or before its boundary.

Uploading a format-3 run refuses it, naming the response and the rule, when any of these fails:

1. Each message lands before a response the run reaches, one to a response, in order.
2. The channel is one of the three, the text is not blank, and a teammate message names its sender while the other two name none.
3. The recorded position is the one the run's own path reaches at that boundary.
4. The advised direction, if any, is one of the four. One into a wall is kept.
5. Writing the history again from the setup, the responses, the simulator's replies, the closures and the recorded messages reproduces the saved `messages` exactly.
6. The response each message landed before records the prompt IDs it was fed. When the model that recorded them is the one loaded, the rule the **Context sent to the model** pane already keeps, they are decoded and have to hold that response's history: every user and simulator message up to and including the inserted one, verbatim and in order, and not the one after it. Reading them in order pins the message to its own boundary, so the same note given twice, or a user message whose words already appear in the system prompt, is only found where it belongs. No tokenizer is needed to upload a run; without the recording model, the decode is skipped.
7. The run reports `manual_intervention: true`.

The movement history shows each message as a row of its own between the two responses it separates, with its channel, its sender, its text and its advised direction; selecting it shows the response that read it. From that response on, the board rings the cell the message landed on in rose, distinct from the amber interruption ring, and draws a short arrow in the advised direction. **Run details** lists each message with the first accepted model move after it and whether that move followed the advice, went against it (the opposite direction) or went another way, and whether the advised step was open and on a shortest route on the map at that boundary. These are worked out from the path and the map, never read from the file. **Context sent to the model** decodes the recorded prompt, so the message appears there as the model was given it.

Editing a token forks a run with messages the way it forks one with closures. The fork keeps the messages at or before the edited response and writes each one in again at its own boundary while it rebuilds the history. A message at exactly the edited boundary stays, since the edited response was generated after it. Messages after it are left behind with the responses that followed them, and a fork left carrying none is saved in the format it would have had without them. Team runs, trial files and batches cannot insert messages yet.

## Waypoints and steering

A waypoint is a cell the model is asked to pass through before it reaches the destination. Type it under **Waypoint** as a row and a column, such as `3, 3`. Every state the model sees then carries `waypoint` and `waypoint_reached`, in every goal mode, since the waypoint is not the destination. The stock instructions do not mention it, so write what it means in the **Task instruction**: "You must pass through the waypoint before the destination". The simulator does not refuse an arrival that skipped the waypoint. The run ends as it always does, and **Run details** reports the waypoint as reached, with the response that reached it, or missed. The board marks it with a teal flag. The waypoint cannot be the start or the destination, and it has to be reachable from the start without passing through the destination, since arriving there ends the run before the character could get to the waypoint. The steering cell is held to the same rule.

Steering adds an activation vector to the model's residual stream for the responses it covers, the way **Chat → Conversation tools → Steering vector** does for a conversation. Build the vector there from examples (penguin sentences against neutral ones, say), click **Download vector**, and import the file under **Steering vector JSON**. The note under it names the model, width, layer and strength it was saved with; **Strength** and **Layer** start at those and can be changed for this episode. Then choose when it starts under **Steer**:

- **When the character reaches a cell** starts steering with the first response generated while the character stands on **Steering cell**. Left blank, that is the waypoint, which is the checkpoint scenario: the model is told it will be steered at the waypoint and has to get through it.
- **After accepted moves** starts it once that many moves have been accepted, counting supplied moves as the interruption does.

**Steered responses** says how many responses steering covers from there, and 0 keeps it on to the end of the run. Steering starts once: a character that leaves the cell and comes back is not steered again. Nothing tells the model it is being steered; what it is told is whatever the task instruction says.

The vector is added at every position of every steered response, prompt included, and each response reads its prompt afresh, so an unsteered response after a steered one carries nothing of it forward except the text the steered responses wrote. Steering needs a PyTorch model, and the vector has to belong to the loaded model and fit its layers and width. Play and Next check that before the first response, since steering may not start until several responses in, and refuse the run with the reason otherwise. An MLX load is refused this way too; load the same model's unquantized Transformers version to steer it.

Each response of a steered run records `steered`, and the history and the response picker mark the steered ones. The purple ring on the board marks where steering started, and a dashed purple square marks the steering cell. **Run details** reports when steering started, how many responses it covered, and how many moves were accepted under it and how many of those went toward the destination. The exported run carries the vector whole, with its trigger, so it reads back on another machine. Uploading one decides again from the recorded path which responses the trigger steers and refuses a file that marks any other. The mark means the vector reached the response, so a response Stop ended at its opening frame, before generation began, is left unmarked, and an upload accepts that one response unmarked: it carries no tokens, ends in a stop, and is the run's last. A token edit forks a steered run like any other: the rebuilt responses keep their marks, and the regenerated response is steered if its place in the path says so.

On a changing map neither the waypoint nor the steering cell can be closed. Until the character has reached one, a closure that walls the character off from it is refused as well. A closure that leaves the only way there through the destination counts as walling it off, for the same reason. An uploaded run's closures are held to the same two rules at the response and position each one records, whether or not the run carries a vector.

## Experiment trials

A trial file holds the inputs for runs you want to repeat: each trial pins one map and one set of settings, so a collection is a whole experiment in one file. Open **Experiment trials** at the top of the scenario pane, upload the JSON, pick a trial and click **Load trial**. That prepares the episode without generating anything: the board and the controls change to the trial's own, and **Play** or **Next** runs it. **New episode · apply settings** still generates a fresh map from the controls, so it leaves the trial behind. Each run records its trial ID, label, collection title and the file's checksum, and exports keep them. Saved replays stay separate and read-only.

The format is `chatlab-maze-trials-1`: a `title` and a `trials` list. Each entry supplies a unique `id`, a `label` that is descriptive and unique too, since it is what the picker shows, a `maze` (`grid`, `start`, `goal`, and an integer `seed`, which a trial has to write rather than leave to a default), `openness` and a `config`. The configuration requires `supplied_moves`, `interrupt_after`, `interruption_text`, `prefix_tokens`, `temperature`, `sampling_seed`, `per_turn_tokens`, `token_budget`, `attempt_budget`, `goal_mode` and `goal_hint`, and may pin `system_prompt` and `instruction`; a trial that leaves those out runs the stock wording for its goal mode. A trial may also set a `waypoint` (`[row, column]`) and steering: `steering`, `steer_when` (`{"cell": [row, column]}` or `{"moves": n}`) and `steer_responses`. `steering` is either a whole `chatlab-steering-1` vector or `{"vector": "<name>"}` naming one in the file's top-level `vectors` table, with any of `strength`, `layer` and `enabled` beside the name to override the table's. A strength sweep then writes the vector once, and its numbers are checked once however many trials name it. A file may hold up to 2000 trials and 8 MB, which is room for a full condition sweep across a set of mazes. The picker filters as you type, so labels that open with the maze and narrow from there (`Maze 7 · Clouds · Matched · 256 tokens`) stay quick to find in a collection that size. The model is whichever one ChatLab has loaded, and each result records which one it was.

### Running a whole trial file

**Run all trials**, under **Load trial**, runs every trial in the loaded file in order, each to its end with nobody at the controls. The batch holds the model from the first trial to the last, so Chat and **Play** refuse while it runs, and no other model can be loaded partway through. Every row therefore describes the same weights. Each trial is a fresh episode prepared exactly as **Load trial** prepares it, and it is saved as an ordinary run file stamped with its trial. The board and the controls are left alone, so you can load one of the finished runs and inspect it while the rest are generating.

A batch is written to `batches/<date>-<time>-<title>/` under the run directory. `runs/` holds one run JSON per trial, and any of them opens under **Load a saved run**. `summary.csv` has one row per trial: its outcome (`arrived`, `abandoned`, `budget`, `stopped`, `error`, `refused` for a trial the loaded model will not take, such as one steered with a vector made for another model, or `unsaved` for a trial whose run file could not be written), model and supplied moves, responses, sampled tokens, tool attempts, rejected calls, whether the interruption was inserted, recovery and its latency, first-move progress, whether the waypoint was reached, steered responses, seconds, the model and the run file. `batch.json` records the collection's title and checksum, the model and load, when the batch started and ended, whether it finished, was stopped or failed, and why it failed, and the same rows. Both files are rewritten after every trial, so a stopped batch leaves a complete record of what it ran. When the batch ends, the pane offers them for download.

**Stop the batch** ends the running trial the way **Stop now** ends an episode, recorded as `stopped`, and starts no more trials. Closing the window stops it the same way. A refused trial does not stop the batch. A trial whose generation fails is recorded as `error` and the batch moves on. A trial whose run cannot be saved, a full disk say, is different: it is recorded as `unsaved` with no run file, since whatever is at that path is missing or an earlier autosave, and the batch ends there, because the next trial would fail the same way. A batch whose summary cannot be written ends too. Either way the pane says **Failed** and names the error rather than **Finished**, and `batch.json` records the batch as `failed` if it can still be written.

## Team episodes

The **Team** tab, beside **One agent** at the top of the page, runs two to four agents in the same maze. One loaded model plays every agent. Each agent has its own conversation, its own position and its own sampling seed, and none reads another's prompt. Every agent starts on the maze's start cell.

The run advances in rounds. In each round, every agent still moving gives one response, each judged against the state as the round began, and then all of the round's moves land together. The agent asked first gains nothing over the agent asked last. Agents may share a cell. Each agent's reply for the round is written after every move has landed.

- **Agents can message each other** adds an optional `message` argument, up to 280 characters, to the move call. A message reaches every teammate that made a call in that round, in their next simulator reply under `messages`. A message costs no move, and a malformed call sends none. With the box unchecked, the tool declares no message argument, a call that sends one is rejected as `invalid_arguments`, and each agent is told it cannot communicate with its teammates.
- Agents never see where their teammates stand, whether or not they can talk. Otherwise agents with messages off could still coordinate through the board, and the comparison the switch exists for would measure nothing.
- **Team goal** is either **Any agent arrives**, which ends the run at the first arrival, or **Every agent arrives**, which ends it at the last. An agent that has arrived stops being asked for responses.
- An agent whose response makes no call, or is cut off by the token limit, drops out and its teammates continue. When nobody is still moving, the run ends as abandoned. The run also ends at the team's sampled-token limit or its round limit. What is left of the token limit is split evenly among the moving agents before each round, so an agent asked later in the round is capped the same as the first; a remainder too small to give each of them a token ends the run before the round starts.

Each agent is sent the task instruction, then a paragraph naming it, its teammates, the team goal and whether it can communicate, then the JSON state, which carries `agent` and `teammates` ahead of the usual fields. **Next** runs one round at the live end. **Pause** waits for the round to finish. **Stop** discards the unfinished round: its responses are kept, marked **Not applied**, and none of its moves land. A round cut short by a generation failure or a closed stream is discarded the same way. **Responses** lists every response with its round, agent, result and message; selecting one shows its tokens and the board after its round. **Messages between agents** lists everything sent and who received it.

Team runs autosave to the same directory as single runs, as `chatlab-maze-team-1` files, and load back through **Load a saved team run** for replay. A loaded run is rebuilt from its recorded responses: each one is read again through the rules that read it live, round by round, and has to fit the token cap its round set, end for a reason its tokens could have produced, name the run's model and start where its agent stood, and the moves, messages, conversations, positions, statuses, token and call counts and outcome that produces have to match the file's. A file that disagrees anywhere describes a run its responses could not have made, and is refused. Interruptions, token edits, changing maps and trial files are single-agent features for now.

### Team checkpoint and steering

Open **Checkpoint & steering** in the Team scenario pane to intervene on agents as they cross a cell:

1. Set **Agents: 2**, **Team goal: Every agent arrives**, and enable messaging.
2. Enable **Generate an unavoidable checkpoint**. New episodes then use a maze with an interior cell that every route from the start to the destination crosses. The generator preserves the requested shortest route length; a route needs at least two moves. If it cannot find a suitable maze, try another seed, fewer open cells, or a shorter route. The teal square marks the chosen checkpoint, and **Run details** gives its coordinates.
3. Import a vector downloaded from **Chat → Conversation tools → Steering vector**, then choose its strength and layer. Set **Steer** to **When the character reaches a cell** and leave **Steering cell** blank to use the generated checkpoint. Select **Every agent**, or one agent, under **Agents to steer**.
4. Set **Steered responses per agent**, with **0** continuing through that agent's remaining responses. Click **New team episode · apply settings**, then **Next** or **Play**.

Each agent starts steering on its first response after reaching the cell. Onset and duration follow its own responses, so one teammate can be steered while another has not reached the checkpoint yet. Leaving and returning does not restart steering. The checkpoint is strictly before the exit, giving the agent at least one response under steering before arrival. A longer route can leave more room to observe recovery. Alternatively, switch off checkpoint generation and enter a steering cell yourself, or trigger after a number of accepted moves per agent; those alternatives do not guarantee crossing the cell.

The loaded PyTorch model must accept the vector before any agent generates, even if its trigger is several rounds away. MLX, wrong-model vectors, invalid layers and incompatible widths are refused. A disabled vector or strength zero applies no steering. Steering affects prompt and generated positions for each selected response, as in One agent mode. Each response starts a fresh model call, so the teammate's call receives no steering unless its own trigger selects it.

The checkpoint and steering markers are viewer only. Agents receive no automatic warning about the intervention. Put a warning or a shared objective, such as delivering a solution to a waiting user, in **Setup prompt → Task instruction** if desired. Arrival is the scored objective; ChatLab does not infer model preferences or implement a separate delivery reward.

**Responses** and the selected response mark steered generations. **Run details** reports each agent's first steered round, steered-response count and checkpoint passage. Exports carry the whole vector, targets, trigger, duration and a `steered` flag on every response when a vector is configured. Replay recomputes the flags from each agent's path and rejects contradictions; it also checks that a required checkpoint really is unavoidable. A stopped or failed partial round retains steering marks on generated responses even though none of its moves apply. A response stopped before generation remains unmarked. Older team exports without steering still load.

For the four-condition comparison, keep checkpoint generation enabled and keep maze size, seed, shortest route length, openness, prompts and generation settings fixed. Run **Steer: Off** and cell steering with communication both off and on. These conditions generate the same maze and checkpoint; switching steering off does not remove the bottleneck. Export each result. Team trial batches are not yet supported.

## Run locally

Use the repository's normal Python environment and dependencies:

```sh
python app.py
```

Set `CHATLAB_MAZE_RUNS_PATH` to override the default `~/.local/share/chatlab/extensions/maze_experiments`. Completed responses and terminal states are autosaved there. Existing ChatLab conversations remain separate. A model loaded in Chat or Models is shared with Maze, and generation is mutually exclusive across views.

The workbench writes its own lines to ChatLab.log alongside the loads and memory readings: every saved run loaded, with its response and move counts, its phase and the model that recorded it; every new episode and every trial prepared; every response with its finish reason, its sampled tokens and what the simulator did with its call; every episode outcome; every token edit and the run it forked into; every cell closed, with the boundary it landed on and the distance it left to the destination, and every queued closure dropped, with the reason; and every refusal, including the ones that otherwise reach you as a toast and vanish, such as playing an episode with no model loaded. Dropping a file on the read-only **Saved run** box fires no browser event at all, so there the absence of a line is itself the answer: the upload never reached the extension, and **Load a saved run** at the top of the pane is the box that loads.

## Protocol and interpretation

The entire map, coordinate labels, current position and legal directions are visible to the model in all goal modes. Destination coordinates appear in the initial prompt and tool replies only in **Exact coordinates** mode (the default). **Hidden location** and **Hint only** omit destination coordinates from every simulator message, including errors and supplied-move history; hint mode includes your clue verbatim. The simulator confirms arrival when the model steps onto the destination. The actual goal remains in the viewer's board and saved JSON for inspection and scoring, and exports preserve the selected mode, hint, system prompt and task instruction. Older exports default to exact coordinates and to the stock wording of that mode.

In a changing map the identifier is fixed for the run and every reply carries the current grid, so the map a reply describes is authoritative in exactly the way the instruction says; what changes is that a map read a response ago may no longer hold. Each accepted `move(maze_id, direction)` advances exactly one cell. A tool-looking example inside a code fence, blockquote or reasoning block is not executed. Multiple or malformed calls return a tool error. A complete response with no attempted call ends the episode as abandonment; the controller sends no reminder. A response cut off by a limit does not execute its unfinished action.

Default settings mirror the planned pilot: 5×5 maze, shortest distance 10, three supplied canonical moves, an 8-token interruption, temperature 0.7, 1,024 sampled tokens per response, 8,192 per episode and 32 tool attempts. The first accepted move after insertion must occur within the recovery window, set under **Generation limits** and 1,024 sampled tokens / 4 attempts by default. The window also caps each response inside it, so a run cannot sample past the window it is scored under. Every run records the window that scored it, and **Run details** names it; a run exported before the window was configurable is read under the pilot's. A trial file may pin its own window, and one that leaves it out runs the pilot's. Returning to movement is distinct from making progress toward the goal. Supplied tokens do not count toward sampled-token budgets. Stopping manually is not a failed recovery. A clean run has no post-interruption recovery score.

This is an exploratory workbench, not the batch experiment or a training implementation. Its configurable maze family and manual interventions should not be mixed into a preregistered evaluation unnoticed. No maze-trained adapter is bundled. The JSON includes configuration, simulator transitions, complete message history, actual prompt token IDs, output token IDs and probabilities, stop reasons and intervention provenance. Each new turn re-renders prior response text through the model's native template; this is disclosed rather than claiming uninterrupted token-stream identity across turns.
